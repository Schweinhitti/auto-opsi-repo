# Automatic private OPSI 4.3 software repository

This self-hosted Docker stack discovers upstream Windows releases, downloads official installers, packages those installers into real `.opsi` archives, generates OPSI repository metadata, and serves the results at **http://HOST-IP:37563/**. Clients install the bundled vendor installer; they do not need WinGet or Internet access for installer retrieval.

The project lives in `/opt/opsi/opsi-auto-repo`. Your existing server at `/opt/opsi/opsi-docker/opsi-server` is separate. Nothing here imports products, changes server configuration, or schedules client deployments without the administrator running the documented integration commands.

## Architecture

- **repo-builder**: Python, official OPSI 4.3 package CLI, immediate startup run followed by a configurable six-hour interval. One product failing does not stop other products. Persistent state and historical installer checksums live in `state/packages.json`.
- **repo-web**: nginx, read-only repository mount, directory listing, GET/HEAD only, HTTP healthcheck, port 37563 on this host. No Docker socket or builder work/state directories are exposed.
- **Catalog**: `catalog/packages.yaml` contains all product definitions, source settings, installer/uninstaller arguments, detection and redistribution classifications. No application catalog is embedded in Python.
- **Publication**: installers download to private `work/`, pass format and checksum checks, enter `CLIENT_DATA`, and are packaged using `OPSI/control.toml`. OPSI extracts each archive again before publication. Complete files are atomically renamed into the repository; metadata is generated outside the served directory, then atomically replaced. Failed metadata generation prevents retention deletion.

Repository files include `.opsi`, `.opsi.md5`, `.opsi.zsync`, `.opsi.provenance.json`, `packages.json`, and `packages.msgpack.zstd`. Metadata is generated by OPSI tooling, not an imitation format. The CLI advertises the newest version per product; older retained archives remain downloadable for recovery. Atomic rename applies per file, not to the entire repository: an in-flight reader may briefly observe old metadata while a new archive is published. Existing version URLs remain available until retention runs.

## Applications

See [the catalog](catalog/packages.yaml) for the authoritative enabled/disabled state and exact options. The included recipes cover Firefox, Thunderbird, Chrome, 7-Zip, VLC, Notepad++, LibreOffice, KeePassXC, Git for Windows, Visual Studio Code, SumatraPDF, PuTTY, PowerToys, RustDesk, GIMP, Audacity, OBS Studio, Python 3.14, Temurin JDK 21 and Everything Search.

VLC and GIMP are disabled because live vendor URLs redirect installers to externally operated mirrors outside the strict vendor-owned-host policy. Their metadata adapters and recipes are retained. FileZilla, Inkscape and WinSCP also start disabled because safe automation or official download routes have not been verified. Disabled records explicitly explain the reason and are skipped. Do not merely toggle them on: complete the source, installer, detection and uninstall configuration first.

Enabled recipes have metadata/download/package validation as recorded in [VALIDATION.md](docs/VALIDATION.md). **Windows client acceptance testing is still required before broad deployment.** A valid OPSI archive does not prove every vendor's installer, upgrade and uninstaller works on your Windows image. Test on a representative OPSI-managed VM, including a second setup, an upgrade and uninstall. Current recipes target machine-wide Windows x64; ARM64 and x86 clients are not supported. Firefox/Thunderbird use en-US builds. Configure language URLs explicitly if required.

This installation uses **HTTP_PORT=37563** in `.env`, selected as a free port with administrator authorization. The Compose default remains 8088 for fresh installations; integration URLs below use this host's selected port.

## Requirements and installation

Use a Linux host with Docker Engine and modern Compose (`docker compose`), HTTPS access to the official source hosts, and adequate disk space. Plan for at least 15–25 GB for the initial catalog plus retained versions and temporary copies; actual space depends on enabled products. The builder image contains official OPSI server tooling but never starts OPSI server processes. Linux amd64 and arm64 hosts can build Windows x64 packages.

```bash
cd /opt/opsi/opsi-auto-repo
cp -n .env.example .env
mkdir -p repository state work
# Set BUILDER_UID and BUILDER_GID in .env to these directory owners:
id -u
id -g
# Edit .env if your UID/GID differs from 1000:1000.
docker compose config --quiet
docker compose up -d --build
```

The builder starts its first full run immediately. Monitor it:

```bash
docker compose logs -f repo-builder
curl -f http://HOST-IP:37563/
```

On this prepared workspace some packages may already exist from validation; they will be checked and skipped. The default bind address is all interfaces. Restrict port 37563 to your depot network before using this as a private repository, or set `HTTP_BIND_ADDRESS` to the host's LAN address. This server has no authentication or TLS termination by default. Put it behind an authenticated HTTPS reverse proxy if needed.

## Configuration

| Variable | Default | Meaning |
|---|---|---|
| `UPDATE_INTERVAL_SECONDS` | `21600` | Delay after a cycle completes; minimum 60 seconds |
| `KEEP_VERSIONS` | `2` | Number of complete product-version/revision archives to retain, at least 1 |
| `GITHUB_TOKEN` | empty | Optional read-only GitHub token; improves unauthenticated API limits |
| `ALLOW_CHANGED_CHECKSUM` | `false` | Explicitly permit a changed installer hash for a known version |
| `MAX_DOWNLOAD_BYTES` | `2147483648` | Maximum size of one installer (2 GiB) |
| `BUILDER_UID`, `BUILDER_GID` | `1000` | Must own writable repository/state/work directories |
| `HTTP_PORT` | `8088` | Host HTTP port; change only if 8088 is already occupied |
| `HTTP_BIND_ADDRESS` | `0.0.0.0` | Host address bound to HTTP_PORT |
| `OPSI_BASE_IMAGE` | `uibmz/opsi-server:4.3` | Official OPSI tooling base; use a reviewed digest for pinning |
| `LOG_LEVEL` | `INFO` | Builder logging level |

Changing environment values requires `docker compose up -d` to recreate affected services. Catalog changes are read each cycle; no image rebuild is needed. Protect `.env` (`chmod 600 .env`) and never commit tokens. The token is sent only to `api.github.com`, never to installer/CDN hosts.

TLS verification is always enabled. To use a private CA, mount a PEM bundle read-only into the builder and set `REQUESTS_CA_BUNDLE` in a `compose.override.yaml`:

```yaml
services:
  repo-builder:
    environment:
      REQUESTS_CA_BUNDLE: /certs/ca-bundle.pem
    volumes:
      - ./certs/ca-bundle.pem:/certs/ca-bundle.pem:ro
```

The bundle must contain the trust roots needed for all upstream sites. No insecure TLS bypass setting is provided.

## Dry run, manual update and logs

```bash
docker compose run --rm repo-builder --dry-run
docker compose run --rm repo-builder --once
docker compose run --rm repo-builder --once --product auto-firefox
docker compose logs -f repo-builder
```

A dry run fetches small release metadata and published checksum files, reports versions and proposed changes, and creates no installers, packages, locks or state changes. A normal run exits with code 1 if any selected product or repository metadata operation failed, 2 if another builder holds the lock. The periodic service logs failures and retries on the next cycle. To perform a manual build during a scheduled run, wait for completion or stop the periodic builder first:

```bash
docker compose stop repo-builder
docker compose run --rm repo-builder --once
docker compose up -d repo-builder
```

Each cycle prints Updated, Unchanged, Failed, Warnings and Disabled lists. `state/last-run.json` records the latest non-dry-run summary. Monitor its timestamp as well as the nginx healthcheck: nginx can remain healthy while upstream builds fail. Docker logs rotate at 10 MB, three files per service.

## Adding a package

Add an entry under `packages:`. Use a unique lowercase OPSI product ID no longer than 32 characters, a positive integer revision, exactly one x64 architecture, and explicit official hostname allowlists. Example schema (replace example URLs with verified vendor endpoints before enabling):

```yaml
id: example
opsi_product_id: auto-example
name: Example Application
description: Example Windows application
enabled: true
architecture: [x64]
redistribution: unknown
package_revision: 1
source:
  type: direct_url
  version_url: https://vendor.example/releases.txt
  version_regex: '(\d+\.\d+\.\d+)'
  download_url_template: https://vendor.example/releases/{version}/installer.exe
  allowed_hosts: [vendor.example]
installer:
  type: exe
  silent_args: [/S]
detection:
  method: registry
  display_name_regex: '^Example Application$'
uninstall:
  method: registry
  silent_args: [/S]
```

Run unit tests and a product dry run, inspect generated sources, then perform a real build and Windows acceptance test. URL allowlists check every redirect; a vendor moving to a new CDN will deliberately fail until its official status is reviewed. Avoid broad wildcards. For shared hosts such as GitHub, add `allowed_url_prefixes` to a WinGet recipe to bind initial installer URLs to the verified project.

### Source adapters

`builder/builder/sources/adapters.py` exposes `resolve(package, http) -> Release(version, url, sha256, architecture, filename)`; `sources/base.py` defines the extension protocol. Dispatch and catalog values are separate. Add a new adapter branch and its catalog validation/source tests when a vendor needs a new metadata protocol.

Supported types:

- `github_release`: official REST API, stable releases, configured owner/repository or `repo`, full-match asset regex, architecture substitution, optional tag selection and optional checksum asset.
- `direct_url`: configurable regex over a vendor version feed, numeric version ordering, optional track, download template and SHA256 endpoint.
- `mozilla`: JSON version field plus Mozilla archive URL and published checksums.
- `videolan`, `documentfoundation`: explicit official release-directory parsers; no third-party download-site scraping.
- `microsoft`: VS Code's stable update API with published SHA256.
- `vendor_json_api`, `adoptium`: dotted JSON paths (numeric array indexes supported) for version, URL and SHA256; Adoptium uses `java_version`.
- `winget_manifest`: Microsoft's official GitHub repository only, stable version selection, architecture/type/machine-scope filters and required `InstallerSha256`. It discovers metadata and downloads the installer; it never installs WinGet or calls it on a client. Versions may lag the vendor. Installer arguments remain reviewed catalog values rather than blindly imported manifest commands.

### GitHub packages

```yaml
source:
  type: github_release
  repo: rustdesk/rustdesk
  release_type: latest
  prerelease: false
  asset_regex: 'rustdesk-.*-x86_64\.exe'
  allowed_hosts:
    - github.com
    - release-assets.githubusercontent.com
    - objects.githubusercontent.com
```

The newest parseable release in the most recent 30 API release records must contain exactly one matching asset. Missing assets fail rather than falling back to an old version. Use `release_type: tag` and `tag: ...` to pin a release. `version_regex` captures vendor-specific tag versions, `architecture` can populate `{architecture}` in asset expressions. `checksum_asset_regex` selects a release's checksum asset. Standard SHA256SUMS syntax is the default; `checksum_line_regex` supports alternate formats with `{filename}` and SHA256 as capture group 1 (Audacity uses a filename/length/hash table). GitHub's `sha256:` asset digest is verified when supplied. Detached PGP signatures are not automatically trusted without pinned signer keys.

GitHub 403/429 responses report access/rate-limit status without disclosing tokens. Transient 429/5xx responses receive bounded retries with backoff; long rate-limit waits are deferred to the next scheduled cycle. GitHub HTML is never scraped.

### Direct and JSON downloads

`download_url_template` supports `{version}`, `{version_compact}` and `{architecture}`. `version_regex` must capture the actual version in its first group. `track: '3.14'` filters numeric major/minor branches. If a JSON API exists, use `vendor_json_api` with `api_url`, `version_field`, `url_field` and optional `sha256_field` instead of HTML.

`checksum_url_template` supports `{version}` and standard SHA256SUMS files; set `checksum_filename_template` when the checksum entry includes relative subdirectories. Only the selected filename's checksum is accepted, never the first arbitrary hash in a multi-file list.

## Version tracking and revisions

Upstream versions are retained verbatim in state and provenance. Python `packaging.version.Version` provides semantic ordering, so 10.0 follows 9.9. Unknown version formats fail instead of using lexical ordering. Leading `v` and insignificant leading zeroes normalize; beta identifiers normalize to PEP 440 notation. Local/build labels are reversibly encoded with `.local.` for OPSI; Git's `.windows.` suffix is retained. Product versions exceeding OPSI's 32-character limit are rejected. Normalization collisions with an existing package's provenance fail visibly.

Python remains on the configured 3.14 identifier and track. To move branches, edit both intentionally; consider using a separate OPSI product for side-by-side Python branches. Temurin stays on `source.java_version: 21`. The original upstream version and a separate integer `package_revision` determine packaging. Increase `package_revision` whenever deployment logic changes without an upstream update. A Firefox 143.0 revision 2 archive is `auto-firefox_143.0-2.opsi`.

The builder checks existing `.opsi` names as well as state and provenance. It blocks downgrade attempts from stale feeds or lower catalog revisions. Missing state does not cause duplicate archives. Archives with provenance are checked for corruption before being skipped. Do not mix arbitrary manually renamed archives into this managed directory.

## Checksums, signatures and force rebuilds

Every download records SHA256, size, original source URL, timestamp, vendor, upstream/OPSI versions and signature status. Mozilla, Microsoft, WinGet, Adoptium and configured vendor checksum files are checked against the actual payload. GitHub asset digests and configured SHA256 release assets are checked when present. EXE/MSI magic and ZIP/MSIX structure are validated; HTML error responses cannot become installers.

Historical installer SHA256 values remain in state even after old archives are pruned. Archive provenance can recover the retained versions' evidence after state loss. An unexpected hash change for a known version fails prominently. `--force` does **not** bypass this guard:

```bash
docker compose run --rm repo-builder --once --force auto-firefox
docker compose run --rm repo-builder --once --force-all
```

Force selects rebuild behavior, not the product filter: use `--product auto-firefox --force auto-firefox` to check only that product. Prefer incrementing the package revision over replacing an existing version URL, especially while depots are downloading. Replacing the same URL can leave HTTP caches or an active client holding mismatched old sidecars. If an installer genuinely changed, investigate first, preserve the old artifact and state, increment the revision, and use a one-off `-e ALLOW_CHANGED_CHECKSUM=true` override only after explicitly accepting it. Restoring state is required if all historical checksum evidence is lost; no system can compare against evidence that no longer exists.

Linux `osslsigncode verify` logs `SIGNED` on successful verification, `UNSIGNED` when no signature is found, and `UNKNOWN` when trust/tool/format verification is inconclusive. `UNKNOWN` is not proof of authenticity. This is advisory, not Windows publisher enforcement, online revocation enforcement, or a malware scan. Archive MD5/zsync files provide OPSI transfer compatibility; SHA256 provides installer validation.

### Offline packaging-revision recovery

When upstream metadata is unavailable but only packaging logic changed, increase the catalog revision and reuse an already verified bundled installer:

```bash
docker compose stop repo-builder
docker compose run --rm --entrypoint python repo-builder -m builder.repackage auto-git
docker compose up -d repo-builder
```

This separate recovery command verifies the existing archive and extracted installer against their recorded SHA256 values, preserves the original download timestamp/version, and requires a higher revision. It explicitly does **not** check upstream or claim a new software release. Normal periodic updates always check upstream.

## Detection, installation and uninstallation

Generated OPSI scripts run the bundled PowerShell helper using `%ScriptPath%`, native 64-bit Windows PowerShell, quoted paths and captured exit codes. No downloaded script is executed by the builder. Client payload helpers are generated solely from this trusted catalog/project.

Detection supports both HKLM uninstall registry views, `msi` with `product_code`, `file_version` with an environment-expandable `path`, or `custom` with an OPSI script override. Registry regexes must be specific enough to avoid matching other products. `detection.version_from_display_name_regex` captures the software version from DisplayName when a bootstrapper uses a different DisplayVersion (Python). `detection.version_replacements` maps vendor version separators for both target and installed versions (Git). JSON sources may provide `detection_version_field` independently of the package version, followed by `detection.version_regex` extraction (Temurin). Numeric versions equal to or newer than the requested version skip installation. Successful installations must pass version detection; unknown versions fail conservatively rather than claim success. Reboot exit codes 3010/1641 are recognized and logged; reboot scheduling remains OPSI administrator policy. Some vendor installers can reboot themselves despite flags; validate their behavior in your environment.

EXE and MSI recipes use catalog-reviewed silent arguments; MSI runs through `msiexec /i`. Vendor in-place upgrades are the default. `installer.uninstall_previous: true` supports vendors requiring removal first (PuTTY's current manifest). Uninstall supports registry quiet commands, MSI GUID removal, explicit vendor path/command, ZIP directory removal and MSIX deprovisioning. An ambiguous unquoted registry command fails instead of guessing its executable path. Per-package `uninstall.display_name_regex` can override matching for removal. Post-uninstall detection fails if the application remains installed.

ZIP recipes set `installer.target_dir` to a dedicated application directory and use file-version detection. Archives are extracted under `work/` only after traversal, drive-path, symlink and expanded-size checks. ZIP upgrades overlay the vendor payload; they do not remove files the vendor removed from a newer archive. Use an override if that is required. MSIX uses `Add-AppxProvisionedPackage` for machine provisioning and `uninstall.package_name` for deprovisioning; dependencies, licenses, existing per-user registrations and app-specific detection require catalog overrides. There is no enabled generic ZIP/MSIX desktop recipe claiming these application-specific details are universal.

### Package overrides

Place trusted Jinja templates under `catalog/overrides/<opsi_product_id>/`. Optional files `control.toml.j2`, `setup.opsiscript.j2`, `uninstall.opsiscript.j2` replace the matching template. Catalog fields `pre_install_opsi_script`, `post_install_opsi_script`, `pre_uninstall_opsi_script`, and `post_uninstall_opsi_script` refer to files relative to that product's directory. Available template values include `p`, `version`, and `revision`.

For `detection.method: custom`, `detection.script` names an OPSI snippet that owns detection and conditionally invokes `Winbatch_install`, including failure handling. It replaces the standard setup detection/exit-code block, so review it as executable administrator code. Overrides may not traverse outside their product directory. Catalogs and overrides are trusted code, not a safe input format for untrusted users.

## Retention, temporary data and recovery

`KEEP_VERSIONS=2` keeps the newest two version/revision archives per product. It always retains the newest archive and removes old MD5/zsync/provenance sidecars together with the archive, logging deletions. The new metadata is generated successfully before old files are removed. Network failures leave working packages available.

Only one writer runs at a time using a file lock. Finished work directories are cleaned; crash-leftover product/metadata directories are cleaned on the next normal startup under that lock. OPSI's extracted CLI runtime cache remains within `work/` during a cycle and is rebuilt after cleanup in the next normal cycle. Temporary files and publication staging names are hidden from HTTP.

## Add the repository to OPSI and automate depot imports

Follow [the exact integration commands](docs/INTEGRATION.md) for `/opt/opsi/opsi-docker/opsi-server`, including repository configuration, active-repository/product listing, initial import and future updates. **HOST-IP must be reachable from the OPSI container.** Do not use loopback for this separate service.

The systemd service/timer in `systemd/` imports new packages and updates every six hours with random delay. On this installation it was enabled at the administrator's subsequent request. Repository rebuilding and OPSI depot importing are separate jobs. `autoSetup = false` stays the default: enabling it can schedule client deployments and remains an explicit administrator choice.

## Security and redistribution

TLS verification, explicit redirect allowlists, bounded metadata/download sizes, bounded retries, download timeouts, filename isolation, ZIP validation, no shell-based Linux subprocess commands, read-only nginx mounts and an unprivileged builder limit common failure paths. Run the repository on a trusted network: the default HTTP endpoint offers no transport integrity against a network attacker. Use HTTPS and trusted certificates for untrusted network paths. Protect Docker access because it grants host-level privileges; neither service mounts its socket.

`redistribution` is one of `allowed`, `internal_only`, `unknown`. These are administrator classifications, not legal determinations. Both `internal_only` and `unknown` permit building for private/internal use and emit a warning; that does not grant a license or override terms restricting automation or internal use. Verify installer redistribution rights before exposing the repository publicly. `allowed` should only be set after review of the actual applicable license and obligations. Bundling an open-source installer does not automatically fulfill its corresponding-source or notice requirements. Disabled FileZilla entries avoid asserting unverified permission.

## Troubleshooting

- **Port 8088 already allocated:** another service owns the required host port. Free it deliberately or set `HTTP_PORT` to an available port and update all depot URLs consistently. The project never stops an unrelated container.
- **Permission denied:** match `.env` UID/GID to the writable bind-mount owners. Do not use world-writable repository directories.
- **Builder already active:** a scheduled/manual build owns the lock. Wait or stop the periodic service before a manual update.
- **403/429 GitHub:** configure an optional read-only token or wait for the next cycle. Do not treat rate limiting as a new version.
- **Untrusted source host:** inspect the redirect through official vendor documentation, then narrowly update the allowlist. Do not add arbitrary mirror domains to make a failure disappear.
- **Checksum changed/mismatch:** retain the known-good package, investigate upstream changes or compromised content; do not blindly force.
- **No matching latest asset:** upstream changed names/types; update the regex and installer recipe together. The builder does not silently select stale assets.
- **Package created but metadata failed:** archives remain intact; a later successful cycle regenerates metadata before retention. Read `Failed: repository` in the summary.
- **Windows install exits 0 but product fails:** version detection did not confirm installation. Review the vendor's actual registry/file version and refine the catalog. Do not suppress the check.
- **OPSI sees no packages:** verify the reachable HOST-IP, port/firewall, nginx listing, metadata, and `local_auto` repository configuration. A host-local successful curl does not prove container reachability.
- **OPSI CLI changes:** inspect `docker compose run --rm --entrypoint opsi-cli repo-builder package make --help` and corresponding metafile help; do not guess options.

## Backup and restore

Back up **`catalog/`, `repository/`, `state/`, and `.env`** together. Include custom CA bundles, Compose overrides and this project's source if customized. `work/` does not need backup. Stop `repo-builder` during a filesystem backup or use a consistent snapshot; preserve file ownership and historical checksums.

Restore those directories, match UID/GID, verify checksums/provenance and run a dry run before restarting the periodic builder. Losing state removes historical checksums for already-pruned versions; retained provenance can only recover versions still present. Never erase state to bypass a changed-checksum error.

## Updating the stack

Back up configuration and state, review application/source changes and increment package revisions for packaging changes. Then:

```bash
cd /opt/opsi/opsi-auto-repo
docker compose stop repo-builder
docker compose build --pull repo-builder
docker compose pull repo-web
docker compose run --rm repo-builder --dry-run
docker compose up -d
docker compose logs -f repo-builder
```

For controlled production updates, pin tested builder and nginx image digests. Re-run tests and a representative Windows install/upgrade/uninstall acceptance cycle after changing templates or vendor installer types.
